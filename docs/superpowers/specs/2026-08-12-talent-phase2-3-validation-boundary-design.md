# 天赋第二、三阶段验证边界设计

## 背景

天赋垂直切片原计划将主动天赋、中场备牌的服务端能力放在第二阶段，将正式 UI、AI、反馈与玩法验证放在第三阶段。第一阶段完成后确认：这种分层可以继续保留，但第二阶段缺少客户端交互入口，无法独立进行真人端到端验收。

本设计明确第二、三阶段的开发、验证、分支和合并边界。它不改变既有玩法规则、异化预算、隐私原则或 Room 唯一权威架构。

## 已确认决策

- 第二阶段不增加临时 UI、调试面板、快捷键或编辑器直开入口。
- 第二阶段把主动天赋、三项锚点天赋、中场备牌和正式 `Room` / `GameServer` 接线实现完整。
- 第二阶段不执行新增能力的 WebSocket 全链路集成验证、Dedicated Server 真人验证或 Unity 人工交互验证。
- 第二阶段只以纯 C# policy、tracker、规则、状态机、协议模型测试和编译检查作为代码检查点证据。
- 第二阶段完成后不合并 `master`；第三阶段继续使用同一功能分支。
- 第三阶段完成正式 UI 后，统一验证第二、三阶段的联机、交互、断线恢复、AI 和视觉行为。
- 第三阶段必须先合并回 `master`，再从 `master` 构建客户端和 Dedicated Server 进行真人验收。

## 第二阶段边界

第二阶段仍实现生产代码，包括：

- 不关闭基础麻将动作的补充天赋动作模型；
- `藏锋`、`截流`、`定心` 的规则、状态和服务端校验；
- 同一 `decisionId` 下的天赋动作资格校验与普通动作独立提交；
- 第 4 小局后的 45 秒并行中场备牌状态机；
- 预算重算、锁定天赋、超时、断线、非法提交和重连只读状态；
- 协议消息、快照字段和 `Room` / `GameServer` / `TalentMatchRuntime` 正式接线。

第二阶段明确不实现：

- 主动天赋按钮、目标选择器和技能提示；
- 中场备牌页面；
- 异化值档位选择器和预算条；
- 任何只为阶段内人工验证而存在、随后会被删除的交互入口。

第二阶段结束时称为“代码检查点”，不称为可发布、可试玩或端到端完成。检查点允许记录尚未执行的联机与人工验证，但不得把缺失证据描述为已通过。

## 第二阶段验证范围

第二阶段新增测试只覆盖可独立验证的纯 C# 行为：

- policy 输入输出和错误码；
- tracker 的席位、阶段、deadline、重复提交和锁定规则；
- 三项锚点天赋的次数、层数、克制与结算约束；
- 中场生效集合、预算、锁定天赋、超时和断线回退；
- 协议消息与快照数据的序列化结构；
- 客户端临时选择不进入权威状态的纯状态模型。

仍运行现有完整回归与编译，保证旧功能没有被已有测试发现的破坏；但不为第二阶段新增真实 `Room -> GameServer -> TalentMatchRuntime` 联机场景作为验收条件。生产接线的端到端正确性统一由第三阶段验证。

## 第二阶段分支上的临时行为

第二阶段代码不会进入 `master`，因此允许功能分支暂时存在以下不可试玩状态：

- 真人客户端没有主动天赋触发入口；
- 半庄和全庄完成第 4 小局后进入中场，真人只能等待 45 秒超时并锁回原生效集合；
- 单局、东风局和基础麻将动作仍应保持可运行，但不以第二阶段真人测试作为完成证据。

这些状态只允许存在于贯穿第二、三阶段的功能分支，不允许作为正式版本交付。

## 第三阶段边界

第三阶段在同一功能分支上完成：

- 牌库编辑器 6 主 + 3 备选展示；
- 40 / 80 / 120 异化值预览、房间创建档位选择和超限反馈；
- 本家与已知对手天赋展示、实时技能提示；
- 与基础动作并存的主动天赋按钮和目标选择；
- 全屏中场备牌页面；
- 结算贡献拆分、AI 构筑与主动决策、telemetry 和玩法测试材料。

第三阶段同时承担第二、三阶段的统一验证责任，包括真实 `Room` / `GameServer` 集成回归、客户端状态投影、WebSocket 消息顺序、Dedicated Server、真人交互、AI、超时、断线重连和隐私边界。

## 合并与真人验收流程

第三阶段使用两级关口：

1. **合并前自动关口**
   - 第二、三阶段自动测试全部通过；
   - Unity 项目和 NetworkRegression 编译通过；
   - 全分支审查没有未解决的 Critical / Important；
   - 工作区和计划检查项一致。

2. **合并后真人关口**
   - 将功能分支合并到 `master`，但暂不删除功能分支；
   - 从 `master` 重新构建客户端和 Dedicated Server；
   - 在 `master` 上进行真人联机、半庄中场、主动天赋、AI、超时和断线重连验收；
   - 若发现问题，回到保留的功能分支修复、复审并再次合并到 `master`，然后重建和重验；
   - 真人关口全部通过后，才将第三阶段和整个垂直切片标记完成，并删除功能分支。

合并到 `master` 在这里代表“生成真人验收候选版本”，不等于最终完成声明。

## 计划文档调整要求

后续实施计划修订应做到：

- 将第二阶段 Completion Gate 改为明确的代码检查点，列出推迟到第三阶段的验证项目；
- 删除第二阶段中任何要求通过正常客户端人工操作证明功能完成的措辞；
- 保留第二阶段生产接线任务，不把它退化为只写模型的原型；
- 在第三阶段加入统一的第二、三阶段集成验证任务；
- 把第三阶段的真人验收明确放在合并 `master`、重新构建之后；
- 把功能分支删除安排在合并后真人验收全部通过之后。

## 成功标准

- 第二阶段可以在没有 UI 的情况下形成可追踪、可编译、纯逻辑测试通过的代码检查点；
- 第二阶段不会单独进入 `master`；
- 第三阶段 UI 不建立第二套规则或客户端权威路径；
- 第二、三阶段最终通过同一套真实生产链路验证；
- 真人验收使用 `master` 构建产物，失败修复可追踪并重复合并、重建和验证；
- 只有合并后真人验收完成，整个天赋垂直切片才宣告完成。
